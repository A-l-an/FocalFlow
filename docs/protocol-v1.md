# FocalFlow protocol v1 — capture ownership contract

Both repositories implement this version together. UTF-8, one JSON object per newline. Legacy missing-context messages and unsolicited/unknown/expired request IDs are rejected; no compatibility fallback.

## Header and identifiers

Every control, UI/Talk request and UI/Talk response contains `protocolVersion: 1`, `requestId`, and `context`:

```json
{"sessionId":"00000000-0000-4000-8000-000000000099","taskEpoch":1,"snapshotSeq":1}
```

`protocolVersion` is an integer exactly 1. Context has exactly those three keys. Session is a lowercase UUID-shaped string, newly generated by Android for each successful connection. Epoch/sequence are JSON integers in [0, 9007199254740991]; booleans, floats and numeric strings are invalid. `requestId` is a 1–128 character ASCII `[A-Za-z0-9_-]` string; production Android uses UUIDs. Within a context, backend remembers up to 256 admitted IDs; duplicate/excess IDs are rejected. These identifiers are not authentication or credentials.

## Messages and state

- `ROLE`: `PID`, `TaskID` retain validated ASCII identifiers. First ROLE establishes the connection session; subsequent ROLE must retain session and strictly increase `taskEpoch`. `taskEpoch > 0`, `snapshotSeq == 0`. Repeating a task is a new epoch. After valid ROLE admission, Python immediately sends `SESSION_READY` through the bounded writer, outside the control lock and without business/model work. Before each write it rechecks the originating connection, exact context and ROLE request ID.
- `SESSION_READY` (Python → Android): exactly `{type, protocolVersion, context, requestId}`. Version must be integer 1; context and request ID must match the current outstanding ROLE and its current socket/writer. Payload/error/extra fields, duplicate keys, stale or late ACKs are not readiness. A duplicate valid ACK has no further effect. Android exposes connected state and a fresh-capture notice only after this ACK. A new task withdraws current readiness and requires a new ACK, while retaining whether this socket ever had an acknowledged session.
- `INVALIDATE_CONTEXT`: same session/epoch, strictly greater `snapshotSeq`. A new admitted capture advances ownership only after the preceding build/request/apply chain completes. Explicit cancellation and timeout also advance ownership. Ordinary content notifications, window/scroll triggers, double taps and opening a TalkBack menu never cancel an active chain. Clears pending ownership and classification base; native filtering becomes inactive. No control acknowledgement.
- `REQUEST_UI_UPDATE`: exact current context, sequence > 0, fresh request ID, optional `interaction`. New registered intent supersedes any previous intent even in the same context. At most one executing business worker and one latest pending work item on Python.
- `REQUEST_TALK`: exact current context and fresh request ID, plus `baseRequestId` of the successful Decision/UI request that produced this context's classification. Busy or invalid base returns `TALK_RESPONSE` with static `error: INVALID_BASE_OR_BUSY` without stealing the active UI request. No implicit fresh classification or merging across contexts.
- `UI_UPDATE`: matching header, complete `payload` tree; both normal Decision and Talk B use this. Step05 flags-only/source-validation contract remains unchanged.
- `TALK_RESPONSE` with `status: NO_OP`: valid existing Talk A placeholder; no payload and no new action/QA semantics.
- Admitted execution failure: UI uses `UI_UPDATE`, Talk uses `TALK_RESPONSE`, with matching header, static safe error code or exception class in `error`, and no payload. Malformed headers/old controls/unknown contexts are dropped without business work. Stale cancelled work emits no deliberate success. A previously started network send may still arrive and must fail Android's final ownership guard.

Android registers request intent and submits its write in the same tree-manager monitor. Writer queue is bounded to 32; overflow closes/invalidate the connection. One scheduler owns at most the current request timeout (120 seconds); completion/cancel removes its scheduled entry. A second UI/Talk request cannot take an active Android request's ownership; the service retains one latest capture trigger until terminal application. Close, timeout and Future.cancel clear ownership; timeout/cancel also advance context and send invalidation. Talk keeps the original valid Decision base until the context or a newer UI intent changes.

## Snapshot acquisition

The only live Android source is the owned slot:

`/storage/emulated/0/Android/data/com.android.talkback/files/screen_reader_logs/virtual_tree_logs/User_transport/Task_transport/virtual_tree_current.json`

Contents are exactly `{protocolVersion, context, tree}`; tree is the unchanged full capture. The service keeps one active build → publication → request → response application chain and one latest pending trigger, retaining the latest nonnull interaction within the same session/task. Ordinary `snapshotSeq` advances do not invalidate pending intent. A generic scroll/window trigger does not erase a queued click; another nonnull click replaces it and recycles its handle. Task/session changes, pause and disconnect discard old pending intent/interaction. The idle check and capture-token reservation share the request-registration monitor. A concurrently admitted Talk retains ownership; its waiting capture is restored to the latest slot until Talk completes. Queue locks and native traversal stay outside that monitor. Only the active chain can build IDs/native mappings or replace the transport slot. The two-second request rate limit still uses the shared scheduler; a delayed dispatch is part of the same active chain. Window and scroll triggers retain their two-second delay; double tap keeps its existing three-second delay. Content notifications do not schedule captures. Failure, explicit pause/task change/disconnect and terminal application release the chain; a still-current pending trigger can then run. New captures of TalkBack menus/settings remain blocked.

Python pulls this exact slot, validates the expected context/tree before screenshot acquisition, pulls it again afterwards and requires the same envelope and tree. This checks transport integrity of the admitted capture, not whether the page changed. Tree 8 MiB/10,000 nodes/128 depth limits remain; the envelope adds at most 64 KiB. Offline demo and cross-language tests use this same envelope and admission contract.

## Execution ownership and boundaries

Python `UIListener.read_connection` owns socket reads/control invalidation independently of the serial state worker. Constructor/import starts no workers or service IO; `start_worker` is explicit at the server boundary. `_process_message` uses the same admission code for synchronous injected offline flows. The reader handles explicit control cancellation and records admitted interaction text in a separate task-scoped ledger; it never edits the running agent history. Worker performs lazy task history/catalog reset before the next accepted business work and restores failed/stale request checkpoints before starting newer work. Replies retain the originating connection/context/request, never a mutable global destination.

Validated nonempty string interactions from UI requests survive ordinary invalidation and replacement of the latest pending work. Only the serial worker copies these facts into the existing `action_history` prompt argument; derived model checkpoints do not roll them back. The existing frame/context/request-ID checks precede recording, and duplicate IDs do not record again. Repeated text under distinct accepted IDs remains distinct. ROLE/new session clears the ledger. A task accepts at most 256 interaction entries and 64 KiB total UTF-8 interaction text. An excess request receives `UI_UPDATE` with `error=INTERACTION_HISTORY_LIMIT`, `stage=request`, no payload or interaction text, before it can replace pending work. Existing facts are not truncated or silently reset.

Android ignores `TYPE_WINDOW_CONTENT_CHANGED` in the FocalFlow pipeline; ordinary TalkBack still receives it. Window/scroll/double-tap triggers queue a successor without rejecting the current tree or response. No native event-equivalence evidence is collected on the service capture path. Request headers and validation against the captured source remain required.

A backend ordinary UI request replaces only the bounded pending slot. `_active` remains the worker actually executing until it finishes. Success responses are prepared by the existing state machine and delivered after its focused-tree/history/audio work and final guard check; no fallible old-context state commit follows successful delivery. On the permanently nonblocking socket, the last immediate write and `terminal_sent` commit share the reader condition; select/backpressure waits remain outside it. A delivered request cannot expire again, and a valid Talk may queue immediately while the prior worker finishes returning. Physical worker completion remains a separate `done` signal. A pending Talk still counts as busy. Explicit INVALIDATE_CONTEXT/ROLE/disconnect/stop and finite deadlines can still cancel work before delivery. Both active and pending admission budgets are checked while a provider is blocked.

`Work.check/run/own` guard providers, response serialization/send, focused-state commit and audio boundaries. Audio ownership is reserved under the control condition before external creation/start, then all driver calls happen outside that condition. At most four resources can be reserved. Cancellation only marks/queues metadata; it does not call the driver from the reader.

Native operations on the owned stream do not overlap. The business worker creates/starts the empty stream, checks cancellation, and reads/writes at most 1600 frames per call with checks before and after every chunk. Successful output drains pending samples with stop(ignore_errors=False). Only after all worker operations have returned does it publish finalization. One cleanup lane then optionally aborts cancelled/failed streams and closes exactly once, in sequence. The worker waits for cleanup completion outside the control condition before opening its next resource. Unguarded standalone output also uses write, stop, then close to preserve its tail. This conservative ordering avoids assuming portable concurrent stop/abort/open/close support; see [PortAudio threading guidance](https://github.com/PortAudio/portaudio/wiki/Tips_Threading).

Cancellation stops future chunks after an in-flight native call returns. It cannot retract samples already handed to the driver, interrupt an opaque native call, or guarantee immediate silence during the final drain/buffer. The 1600-frame bound is a submission bound, not a wall-clock latency guarantee. A delayed constructor is checked before start; a delayed empty-stream start is checked before any samples are delivered. A blocked driver retains its worker and bounded resource reservation while the reader remains responsive. Capacity is released only after the sole close returns successfully; an uncertain failed close retains the reservation and is not retried as another native close.

The original Ping.aiff uses this same guarded stream route, synchronously before recording, rather than launching an afplay process that could play during delayed process creation. No global sounddevice stop or process-name kill is used.

Reader-side busy/invalid-base Talk errors and interaction-capacity rejections use a bounded queue of eight pending responses plus at most one in-flight output on one dedicated reply thread. Queue overflow fails/closes the originating connection, never reports success. A separate framing lock serializes this thread and normal state-worker replies without holding the control condition. All replies remain bound to their original connection and header; stale queued rejections are dropped, and a packet already in flight may arrive late. Synchronous embedding has no reader thread and sends rejection replies outside the control condition. A cancelled provider/network call or driver operation may still occupy its owning worker until it returns; retry loop observes cancellation before the next attempt. Finite operation/request policies are specified below.

Android `VirtualTreeManager.captureVirtualTree(context, tree)` publishes only a completed current token. `applyFilteredVirtualTree(context, requestId, candidate)` rechecks context and active request inside the same synchronized method that validates and commits. Receiver retains that monitor through pending lookup/application/completion. FocusProxy checks inactive filtering before consulting mappings and holds that monitor for filtered lookup. The service has one capture producer and one coalesced latest capture; stale/failed builders cannot reactivate filtering. Source mapping writes remain local-only.

## Finite failure and transport policies (Step07)

Initial defaults are configurable policies, not measured latency targets. Backend `FailurePolicy` accepts finite positive seconds for connect=5, read=30, request=120, adb=10, write=5, frame=30, backoff=0.5. `attempts` is a strict integer 1..3 and defaults to 1; it controls explicit chat retry only. All TTS calls are single-attempt and the OpenAI SDK has max_retries=0. Retryable chat failures are connection/timeout, HTTP429 and HTTP5xx; invalid output/auth/config/cancellation never retries. `MobileAgentStateMachine`/`UIListener` accept an injected policy; UIListener also accepts a monotonic clock. No content/model/prompt parameters change.

Provider response hooks reject and close non-2xx responses before either OpenAI's eager error-body read or requests' Response.next/redirect-body processing. Redirect following is disabled; no redirect body is read and no redirected request is sent. Successful chat bodies are bounded to 1 MiB and TTS bodies to 32 MiB, checked before accumulation; every controllable iterator boundary checks cancellation/deadline. Requests uses one-byte streaming chunks so slow-trickle response filling cannot hide the deadline behind an 8 KiB read; the installed OpenAI/httpx iterator uses chunk_size=None to expose available chunks. These bounds do not promise a bound on internal decoder/library allocations. Owned HTTP responses/clients close on failure or completion. Voice failures (no input device, empty recording/transcript, failed recording) are explicit safe failures rather than text fed back as user speech.

An admitted Work records its 120-second deadline before queueing. The reader checks it while providers/native operations are blocked; expiry invalidates work, clears latest pending ownership and can send a correlated `UI_UPDATE`/`TALK_RESPONSE` error `DEADLINE_EXCEEDED`, stage `request`. Other safe failures use a static `error` code plus `stage` (chat/tts/voice/adb) and optional integer HTTP `status`. No exception body, URL or credential is serialized. If sending the failure itself fails, the originating connection closes; the serial worker survives and a reconnected valid request can complete. Superseded/cancelled contexts never regain application ownership.

The request deadline bounds admission/application eligibility, not termination of already-sent provider calls, DNS, or opaque native operations. HTTP connect/read timeouts are individual operation/inactivity settings rather than a total-call timer. Checks before/after calls and between chunks reject late work; cancellation cannot retract an in-flight native block or its last audio buffer. At most one business worker plus one latest pending request remain. Deferred native cleanup retains its bounded lease until the native operation returns; no concurrent native abort/close or process termination framework was added.

All live acquisition/reverse ADB calls use the configured executable, argv, checked exit status and at most 10 seconds (clipped by remaining request time when available). Failed/partial pulls remove only the owned local output, so an old file cannot masquerade as a successful new acquisition. Screenshot cleanup still attempts both owned remote removals, each with its own 10-second cleanup budget even after expiry. The one process-owned current acquisition directory remains bounded and is removed on normal process exit; per-call TTS/voice temporary directories close when their owning call returns.

Python sockets use one fixed nonblocking policy with select; writer lock wait and the entire frame send share a five-second deadline. A partial frame must finish within that limit or the socket closes, preventing another frame from being appended to a truncated response. The reader accepts split/coalesced frames and decodes UTF-8 only after newline; inbound request frames are at most 64 KiB. Incomplete-frame age is measured from its first observed byte, never reset by drip progress, and expires after 30 seconds. Idle listening without a partial frame may persist. Stop closes/shuts down owned client/listener sockets and wakes read/select. Threads blocked in opaque external calls may remain bounded until those calls return.

Android `ConnectionLimits` injects positive millisecond limits: request=120000, connect=5000, write=5000, frame=30000. Each ROLE handshake has an absolute connect-millisecond deadline, including a silent peer; malformed/stale replies do not extend it. Before the first valid SESSION_READY, TCP acceptance alone is not backend readiness (ADB reverse may accept then EOF without a desktop listener). EOF/handshake timeout clears that attempt and continues the bounded local retry delay until explicit pause/off or a backend ACK. After this socket has once been acknowledged, EOF fully withdraws source/filter/mapping state and disables the service, including while a newer task awaits its ACK. Explicit pause preserves the native reader, and explicit resume uses a fresh socket/session. Reader polling stays at most 200ms; request/trailing/write-watchdog tasks retain the existing scheduler and capture rate limit. No heartbeat or content-event cancellation was added.

Whisper is outside these HTTP policies. The unchanged live voice loader calls whisper.load_model("base") on first use and can trigger the library's automatic model download if the cache is missing. The supported/offline-validated setup assumes the model is already cached or explicitly injected. Neither first-load/download nor model.transcribe is covered by the 5/30-second HTTP wrapper; only request eligibility is invalidated at 120 seconds and checked again when the library returns. No actual model download/transcription or forced interruption was tested.

## Local pause and recovery (Step08)

The existing TalkBack menu has a local “Use standard browsing (pause AI)” action
(“恢复标准浏览（暂停 AI）”). Opening that menu invalidates current filtering.
Pausing advances context, withdraws filtering, cancels pending/timer/trailing
capture ownership, closes the AI connection and saves the paused preference.
It does not require a provider response. “Enable AI filtering” (“启用 AI 过滤”)
explicitly clears pause and starts a new connection/capture. Required reconnect
and capture work is separate from discardable speech-notice freshness, so menu
dismissal does not consume the resume operation. Task/session IDs are correlation,
not authentication or a participant-data management scheme.

Capture entry, publication, request and receiver paths reject paused/stale owners.
Optional captured-UI history checks and writes share the manager lock with pause;
native capture already in progress may still finish, and an already locked write
can finish before pause obtains the lock. Pause does not promise deletion of an
existing transport slot or old debug history. Transport initialization/close clears
its owned current/staging files only.

Current execution errors, invalid/empty filtering, timeouts, cancellation and
disconnect withdraw current filtering without setting persistent user pause.
A valid zero-focus source remains valid and uses the native bypass path. Stale
errors/notices cannot clear a newer result. Once a speech notice has entered the
native SpeechController queue, its cancellation is outside these token checks.
Desktop tests exercise the real manager/menu adapter and selected verbatim service
callback bodies with platform boundaries replaced; device menu reachability,
Looper ordering, native focus/TTS and restart persistence remain unverified.

## Evidence boundary

Tests exercise production reader/admission, provider/TTS boundaries, receiver/manager/owned transport on desktop with synthetic fixtures; no actual models/audio/phone/participant data. JVM Java8 source/API signature compilation is not an APK/device build. Capture/event service integration is statically checked. This guards observed generations, not pixel-atomic screenshot/tree correspondence or physical screen changes Android did not observe. Real TalkBack navigation, device scheduling/performance and all runtime failure UX remain unproven.
